# Data models

[Architecture overview](../architecture.md)

Noosphere separates domain models, generated wire messages, internal runtime
models, persistence records and public worker DTOs. Most domain models implement
`coinlib.Writable` and explicit `fromReader`/`fromBytes` decoders. Protobuf
messages wrap many of those canonical bytes instead of duplicating every
cryptographic structure.

## Identities and groups

| Value | Representation | Meaning |
| --- | --- | --- |
| Participant identity key | secp256k1 private key; 33-byte compressed public key | Login, proposal signatures, DKG attestations and encrypted shares |
| FROST `Identifier` | 32-byte serialized value | Participant's position in one group's roster |
| Iroh endpoint ID | 32-byte public identity, displayed as hex or z32 | Transport identity and coordinator pin |
| Iroh server secret | 32 bytes | Restores the coordinator's endpoint identity |
| FROST group key | Compressed secp256k1 public key | Verifies threshold signatures for a generated key |
| FROST private share | Part of `ParticipantKeyInfo` | Participant's threshold-signing secret |
| `SessionID` | Random 16-byte `OnetimeNumber` | One authenticated logical session |
| `AuthChallenge` | Random 16-byte `OnetimeNumber`, also `Signable` | Participant login proof |
| `SignaturesRequestId` | First 16 bytes of the request-details signature hash | Identifies a signing proposal |
| RPC request ID | Random 16 bytes generated by the Iroh adapter | Correlates one transport request and response |

These values cannot substitute for one another. A client Iroh endpoint does
not automatically prove participant identity. A coordinator pin is not a FROST
verification key. RPC IDs and signing-request IDs are unrelated despite their
equal byte lengths.

[`GroupConfig`](../packages/noosphere/lib/config/group.dart) contains an `id`
string and a read-only `Map<Identifier, ECCompressedPublicKey>` sorted by
identifier. It allows
2–65,535 participants. Its fingerprint is `SHA256(group.toBytes())`, binding
the group ID and identifier-to-key mapping in deterministic order. The ID
allows distinct groups with identical rosters.

A group does not have one global threshold or one FROST key. The same roster
can generate several keys with different thresholds. The threshold belongs to
a DKG proposal and its resulting key information. Treat configuration and
signed values as immutable. Noosphere protects its own serialized views and
collection containers; it does not promise deep immutability of dependency
objects. `Signable` caches its hash, so mutation of a retained dependency value
can invalidate the relationship between fields, bytes and signatures.

## Dependency ownership

The following boundary was checked against Frosty 5.0.0 and Coinlib 6.0.1.
Constructors generally retain the objects listed here; freezing a container
neither clones its elements nor transfers their native handles.

| Retained dependency values | Where retained | Ownership contract |
| --- | --- | --- |
| Frosty `Identifier` | Group rosters, room participants, ACKs, events, login snapshots and signing progress | Borrowed native handle with a mutable cached `toBytes()` result. Never edit those bytes or dispose the identifier while retained; mutation also changes equality/order/hash behavior. |
| Frosty `DkgPublicCommitment` | New-DKG commitment pairs and commitment events | Borrowed native handle. The surrounding list is frozen, but elements and their cached byte representations retain Frosty's contract. |
| Frosty `SigningCommitmentSet`, `SigningCommitment`, `SignatureShare` | Signature rounds and replies, including nested login snapshots/events | Commitment-set maps are read-only containers. Their identifiers, commitments and shares remain borrowed native handles; the set's own Coinlib serialization cache is also outside Noosphere's protection. |
| Frosty `ECCiphertext` | `DkgEncryptedSecret`, `EncryptedKeyShare` and their events | Retained Dart wrapper with dependency-owned ciphertext buffers and serialization cache. Do not mutate its encoded bytes or the buffer supplied to its decoder. Decrypting creates a separate secret object with its own lifetime. |
| Frosty `SignDetails` | `SingleSignatureDetails` | Exception to borrowing: Noosphere copies message/MAST arrays and protects the copied object's serialization. The original `SignDetails` remains caller-owned. |
| Coinlib public keys and Schnorr signatures | Groups, ACKs, room/transition records, signing details/results and signed objects | The concrete Coinlib types copy constructor inputs and return copies of key/signature data. Retaining these concrete values does not expose those buffers. Custom subclasses are not covered by that guarantee. |
| Coinlib transaction, Taproot signing details and previous outputs | `TaprootTransactionSignatureMetadata` | Borrowed dependency graph. Noosphere freezes the outer details list, not transaction serialization/hash caches or every nested value. Treat the entire graph as immutable while the proposal exists. |
| Frosty key info, DKG round secrets and signing nonces | Re-exported low-level APIs, direct client state and storage contracts | Runtime-owned native/secret values rather than UI snapshots. Do not dispose values still used by a runtime, share them across isolates, or duplicate nonces for signing reuse. |

Copy a native value's bytes before decoding an independently owned instance.
Dispose only values whose complete lifetime the caller owns. The worker's public
DTOs contain primitive data and owned read-only byte/list copies; use them for UI
state. Decoding a DTO into a domain object creates a new dependency ownership
boundary and does not make that domain graph deeply immutable.

Keep native dependency versions pinned until their ownership behavior and
platform integration tests have been checked. The audited dependency wrappers
expose mutable caches and disposal directly, so a blanket immutable-domain
claim would be incorrect.

## Signatures over protocol objects

[`Signable`](../packages/noosphere/lib/api/types/signed.dart) supplies an
`uncachedSigHash`. `Signed<T>` combines an object with a 64-byte Schnorr
signature. Its encoding is the object followed by the signature; the enclosing
message identifies the object type. `Signed.sign` signs `obj.sigHash` using
one identity key, while `verify` checks the corresponding public key.

This protocol signature is different from a threshold signature. The requester
signs all `SignaturesRequestDetails` to authenticate its proposal; ROAST signs
the message digests in `requiredSigs`.

`AuthChallenge`, `NewDkgDetails`, `DkgAck`, and `SignaturesRequestDetails` use
tagged hashes. Room and transition objects hash canonical bytes containing a
domain string. `SignableHash` holds a caller-supplied 32-byte signature hash.

## Time and expiration

[`Expiry`](../packages/noosphere/lib/api/types/expiry.dart) stores an absolute
`DateTime`, exposes TTL, and can clamp it to a local maximum. Shared binary
`writeTime` stores unsigned 64-bit **milliseconds** since epoch; duration fields
use microseconds. Worker maps and some server snapshot fields independently
use microseconds. Follow each codec rather than assuming one global time unit.

`Expirable` exposes `expiry`; `FinalExpirable` is a simple rejection record.
`ExpirableMap` filters and optionally removes expired entries on access rather
than allocating one timer per value. Persistent server collections disable
automatic removal on reads so expiration can be persisted explicitly.

## DKG values

[`NewDkgDetails`](../packages/noosphere/lib/api/types/new_dkg_details.dart)
contains a unique active name, description, threshold and expiry. Names contain
3–40 Dart string characters; descriptions allow 1,000 characters; thresholds
range from 2 to 65,535. Runtime checks also enforce actual roster size and TTL
policy. `fromBytesAllowExpired` supports historical records; it does not permit
approving an expired attempt.

| Model | Content and purpose |
| --- | --- |
| `DkgPublicCommitment`, `DkgCommitmentList`, `DkgCommitmentSet` | Frosty round-one public contributions and combined set |
| `DkgRound1Secret`, `DkgRound2Secret` | Temporary local secrets, absent from the persistence interface |
| `DkgEncryptedSecret` | `ECCiphertext` wrapping a `DkgShareToGive` for one recipient |
| `DkgAck` | Group key and acceptance boolean, signed with an identity key |
| `SignedDkgAck` | Signer ID and `Signed<DkgAck>`; equality is signer + group key |
| `DkgAckRequest` | Group key and participant IDs whose ACKs are needed |
| `DkgInProgress` | Details, creator, effective expiry, stage and completed participant IDs |

The round-two commitment-set signature covers
`NewDkgDetails.sigHash XOR DkgCommitmentSet.hash`. Recipients verify it before
decrypting shares. ACKs attest possession of a key; their current payload does
not bind an entire membership-transition proposal or DKG transcript.

## Signing proposals and rounds

[`SignaturesRequestDetails`](../packages/noosphere/lib/api/types/signatures_request_details.dart)
contains:

- `requiredSigs`: 1–65,535 unique `SingleSignatureDetails`, in result order;
- `metadata`: structured information about what is being signed;
- `expiry`: the proposal lifetime;
- `message`: an optional explanation limited to 1,024 UTF-8 bytes.

The tagged signature hash covers the complete serialization; the ID is its
first 16 bytes. Changing the explanation changes the requester signature and
request ID, but does not change the threshold digests in `requiredSigs`.

[`SingleSignatureDetails`](../packages/noosphere/lib/api/types/single_signature_details.dart)
contains Frosty `SignDetails` (message digest and optional MAST tweak), master
group key and an unhardened derivation path of at most 255 indexes. `derive`
applies the same path to participant or aggregate key information.

[`SignatureRoundStart`](../packages/noosphere/lib/api/types/signature_round_start.dart)
contains signature index `sigI` and a `SigningCommitmentSet`.
[`SignatureReply`](../packages/noosphere/lib/api/types/signature_reply.dart)
contains the index, mandatory next commitment and optional current share.
Initial replies have no share; subsequent replies contribute to one round
while preparing the next.

`SignaturesRequest` is the client's public outstanding-request projection:
details, creator, effective expiry and `waiting`, `accepted` or `rejected`
status. Submitting replies returns no update, new rounds, or completed
signatures. Completion lists correspond to `requiredSigs` by index.

## Metadata and signed text

[`SignatureMetadata`](../packages/noosphere/lib/api/types/signature_metadata.dart)
uses a one-byte discriminator:

| Type | Model | Validation |
| --- | --- | --- |
| 0 | `EmptySignatureMetadata` | No semantic validation of digests |
| 1 | `TaprootTransactionSignatureMetadata` | Transaction, previous outputs and input details must match requested signature hashes |
| 2 | `MessageSignatureMetadata` | Exactly one matching payload digest, no MAST tweak and no HD derivation |
| Other | `UnknownSignatureMetadata` | Standalone preservation only; rejected in signing requests |

Taproot metadata does not replace host checks of destinations, fees, network,
derivation policy or the correct signing key. Unknown metadata is not a complete
custom-message extension contract; see [generic data](generic-data.md).

[`SignedMessagePayload`](../packages/noosphere/lib/api/types/signed_message_payload.dart)
stores format version 1 and exact UTF-8 text, limited to 1,024 bytes. It rejects
malformed Unicode and trailing bytes. The signing digest is the tagged hash
`Noosphere/SignedMessage/v1` over the text bytes. Text is not normalized or
interpreted as JSON by the library.

[`SignedMessage`](../packages/noosphere/lib/api/types/signed_message.dart)
combines the payload, an x-only-normalized public key and signature.
`fromCompletedRequest` validates the result. Portable JSON includes `format`,
`version`, `text`, `publicKey`, and `signature`. Parsing validates structure;
call `verify()` to verify an imported signature. Export refuses invalid
signatures.

## Stored participant records

[`FrostKeyWithDetails`](../packages/noosphere_client/lib/src/client/frost_key_with_details.dart)
contains `ParticipantKeyInfo`, name, description, ACKs, recovery-share send
times, reconstruction claims and `KeyConstruction`. It includes secret material
and is not a UI DTO. Equality is by group public key.

`ParticipantKeyInfo` contains the private share and public group/participant
information. Its `aggregate` projection can be sent to the coordinator for
share verification without disclosing the private share.

[`ClientStorageSnapshot`](../packages/noosphere_client/lib/src/client/storage_interface.dart)
groups keys, nonces, prepared operations and rejected IDs into one consistent
load. `SignaturesNonces` maps signature indexes to secret nonces and expiry.
`PreparedSignaturesOperation` records ID, `request`/`replies` kind, exact outgoing
payload components, consumed round transcripts and replacement nonces. It
blocks unsafe continuation after ambiguity; it is not an automatic replay job.

`KeyConstructionProgress` stores explicitly received recovery secrets.
`KeyConstructionComplete` contains the reconstructed full private key. This
separate recovery mechanism is not ordinary threshold signing.

## Server, room and worker records

`ServerStateSnapshot` is opaque versioned UTF-8 JSON with `dkg`, `signing`,
`completed`, and `shares` arrays and base64 binary components. The host stores
it by group ID. Full live signing rounds are not checkpointed for resumption.
See [persistence](state-and-persistence.md).

Room models represent pinned invitations, proof transcripts, participants and
frozen rosters. Transition models bind old/new rosters, DKG plans and opaque
host policy bytes. Their fields are explained in
[rooms and transitions](rooms-and-transitions.md).

Worker models contain public strings, timestamps, booleans, signatures and
proposal bytes. `WorkerKeyInfo` contains only group-key hex, name and description.
`WorkerDkgStatus` and `WorkerSigningRequest` preserve proposal bytes to bind
approval to the reviewed proposal. `NoosphereWorkerSnapshot` is a public runtime
projection, not a backup of `ClientStorageSnapshot`.

## HD derivation

[`hd_derivation.dart`](../packages/noosphere/lib/api/hd_derivation.dart) provides
the shared path `[86, coinType, account, change, addressIndex]`, with every
component unhardened. `deriveThresholdGroupKey` derives public group information;
`SingleSignatureDetails.derive` applies the same helper during signing.
The host selects coin/account indexes, persists the exact path and constructs
chain-specific addresses. Ordinary FROST operation has no assembled aggregate
private key available for hardened BIP-32 derivation. A normal hardened BIP-86
wallet path therefore cannot silently replace this threshold-key path.
